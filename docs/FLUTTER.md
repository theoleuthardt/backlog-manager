# Flutter client

The desktop client in `app/` is the Flutter port of the retired web client (epic #247), which now lives in [`backlog-manager-legacy`](https://github.com/theoleuthardt/backlog-manager-legacy). It targets macOS, Windows and Linux, and Android and iOS (#289, see [Mobile](#mobile-android-and-ios)). Design and layout come from [`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md).

## Setup

1. Install Flutter **3.47.6** (the version in [`app/.fvmrc`](../app/.fvmrc) and the `environment.flutter` constraint in `app/pubspec.yaml`). Either [follow the official guide](https://docs.flutter.dev/get-started/install), use `brew install --cask flutter` on macOS, or use [FVM](https://fvm.app) (`fvm use` reads `.fvmrc`).
2. Install the toolchain of your platform and check it with `flutter doctor`:
   - **macOS:** full Xcode (not only the Command Line Tools) and CocoaPods (`brew install cocoapods`), then `sudo xcodebuild -runFirstLaunch`.
   - **Windows:** Visual Studio with the "Desktop development with C++" workload.
   - **Linux:** `clang cmake ninja-build pkg-config libgtk-3-dev libsecret-1-dev`; the token store (`flutter_secure_storage`) needs a Secret Service such as gnome-keyring at runtime.
   - **Android** (only for the mobile build): the Android SDK (Android Studio, or the command-line tools with `platform-tools`, `platforms;android-36` and `build-tools;36.0.0`) and a JDK 17 or 21; accept the licenses with `flutter doctor --android-licenses`.
   - **iOS** (only for the mobile build, macOS only): the same Xcode and CocoaPods as above.
3. `task app:install` fetches the packages.
4. Start a backend (`task db:up`, then `task backend:dev`). A debug build talks to `http://localhost:8000` by default; the sign-in screen can change the server (`lib/api/server_url.dart`).
5. With FVM, run `fvm use` in `app/` and put `app/.fvm/flutter_sdk/bin` first on your `PATH`: the tasks call `flutter` and `dart` from the `PATH`.

## API client

`app/lib/api/generated/` is generated from `backend/openapi.json` with [`swagger_parser`](https://pub.dev/packages/swagger_parser) (pure Dart, no Java) into `retrofit` clients and `json_serializable` models, and is **committed**, like the web client's `schema.d.ts`: a backend route change shows up as a diff in the PR and, where a field was removed, as a compile error in the code using it. After changing a backend route run `task backend:openapi` and then `task app:generate-api`.

The hand-written part is `lib/api/api_client.dart` (`createApiDio`: Bearer token from the session, a 401 calls the logout callback) and `lib/api/api_error.dart` (`ApiException.from` turns a failed call into the `detail` message of the backend's error body). The generated models already map the backend's snake_case JSON to camelCase fields.

`lib/api/sse.dart` reads the progress streams of the sync and import endpoints: `openSse(dio, path)` yields typed `SseProgress`, `SseDone` and `SseError` events (ending after the first terminal one, `SseStreamEndedException` if the stream closes without one), and cancelling the subscription closes the connection.

`lib/api/server_url.dart` holds the backend URL logic: `parseServerUrl` (https for any host, http only for loopback, no other protocol), the build-time default (`--dart-define=API_URL=https://api.example.com`, `http://localhost:8000` in debug builds, none in a release build without it), `ServerUrlStore` (remembers the user's choice) and `changeServer` (validates, checks `GET /health`, saves, and calls `onChanged` so the caller signs the user out and clears cached data). The "Change" action on the sign-in screen calls `changeServer`.

`app/pubspec.yaml` overrides `analyzer` to 13.x because the current `build_runner` does not run against `analyzer` 14.5; drop the override once that is fixed upstream.

`compareText` and `compareBase` (`text_order.dart`) stand in for `String.localeCompare`: letters compare without regard to case and accents (so "Ärger" sorts with "A", like the web client's ICU collation), then an unaccented spelling comes before an accented one and the lower-case before the upper-case one. Only Latin letters are folded, other scripts compare by code unit. `stableSorted` replaces the guaranteed stable `Array.prototype.sort`, because `List.sort` is not stable.

Deliberate difference from the TypeScript code: `toNumber` returns null for an empty or padded string where `Number('')` is 0 (the API never sends those).

## Checks on pull requests

`.github/workflows/app.yml` runs when `app/` or `backend/openapi.json` changes: formatting, `flutter analyze`, a check that `lib/api/generated/` matches `backend/openapi.json` (the commands of `task app:generate-api`, then `git diff --exit-code`), all tests without the goldens, and a Linux release build. The golden tests run in a job of their own that uploads the diff images of a failure as the `golden-failures` artifact. The golden images are recorded on Linux, the platform of the CI runner; on macOS or Windows the text edges differ by a few pixels, so run `flutter test --exclude-tags golden` there and re-record with `task app:test:update-goldens` on Linux (or take the images from the `golden-failures` artifact).

`tool/test/run.sh` runs the tests (Linux and macOS; `setsid` is used where it exists): it takes a lock (two test runs at once crash the compiler), runs one `flutter test --no-pub` with one worker per core (`TEST_CONCURRENCY`), puts the run in its own process group with a time limit (`TEST_TIMEOUT` per test, default 60s, `TEST_RUN_TIMEOUT` for the run, default 900 s) and kills the group afterwards, so a hung test leaves no `flutter_tester` behind. The whole suite takes about two minutes on six cores (about 1,800 tests; each widget test builds the app, roughly 0.3 s, and each file costs about 3 s of compile and warm-up). While working run what you changed: `task app:test -- test/features/inspector` takes seconds. On a machine with little memory (the compiler of one run for the whole suite grows to 2 GB and more, and gets OOM-killed on 2 GB) set `TEST_SHARD=1`: one `flutter test` per test directory, one worker at a time.

## Running and debugging

`task app:dev` runs `flutter run` for the host platform (macOS, Windows or Linux) with hot reload: press `r` in the terminal to reload, `R` to restart, `q` to quit. The terminal prints the URL of the Dart DevTools (widget inspector, profiler, logs). VS Code and the JetBrains IDEs with the Flutter plugin start the same app from their run button and attach the debugger; open `app/` as the project folder.

A build for another OS cannot be made on this one (Flutter has no cross-compilation for desktop), so Windows and Linux will be checked by the CI runners of those systems (#282).

## Tests

- Pure logic (sorting, filtering, grouping, themes, ...) is ported from the web client's `src/lib/` with the existing test cases, one Dart file per TypeScript file, under `test/` mirroring `lib/`.
- Widgets get widget tests; reusable components of the UI kit also get golden tests (`matchesGoldenFile`) next to them, for the dark and a light theme.
- Golden images live in `test/**/goldens/` and are committed. After an intended visual change run `task app:test:update-goldens`, look at the changed images in the diff and commit them with the code. Golden tests carry the tag `golden` (`dart_test.yaml`), so `flutter test --exclude-tags golden` skips them and `flutter test --tags golden` runs only them. Golden images are recorded on Linux (see "Checks on pull requests"); do not commit images recorded on another platform.
- A test that expresses the desired behaviour is not weakened to make a run green; change the code.
- **Speed (#396).** `flutter test` starts a process per test file and the first widget test of each pays about a second and a half of warm-up (cold code, first layouts); with 138 files that was roughly a quarter of the CPU time. A run without test files in the arguments (`task app:test`, and CI with `--exclude-tags golden`) therefore runs the files in as many bundles as there are workers: `tool/test/bundles.dart` writes `test/bundles/bundle_N.dart` (not committed, analyzer-excluded, removed after the run), each calling the `main` of many test files in a group named after the file, balanced by the number of tests. Nothing moves: the tests stay in their files, and the same 1837 tests run (compared by name before and after, with the group prefix removed). In a bundle the full name of a test starts with its file, for example `features/library/filter_bar the bar starts without tokens`; to run one test by name give its file and `--plain-name`, which runs that file on its own. Not bundled: golden tests (their image paths belong to their own file, so they run from it with `--tags golden`, as a second phase of a plain run), and a file that changes the whole process or has an asynchronous `main` (the files that load the real font with `loadAppFont`). `TEST_BUNDLES=0` runs every file on its own. A new test file is picked up by the next run. Files in one process must not see each other's leftovers: `test/flutter_test_config.dart` puts the preferences back to what a fresh process has after every test (found when `sign_in_page_test.dart`, which sets mock preferences, ran before `app_shell_test.dart` in one bundle and changed how the theme switch behaved); the result must not depend on how the files are grouped, which was checked with 0, 3, 5, 7 and 12 bundles. Measured on 12 cores: 95 s to 59 s wall time and 756 s to 512 s of CPU time for the suite without goldens.
- To find slow tests: `tool/test/run.sh --reporter json --exclude-tags golden > timing.json` has the start and end time of every test; the first test of a file or bundle is slow because it pays the warm-up, not because of what it checks.

## Building and packaging locally

`task app:build` makes a release build for the host platform: `app/build/macos/Build/Products/Release/backlog_manager.app`, `app/build/windows/x64/runner/Release/` or `app/build/linux/x64/release/bundle/`. `API_URL` sets the default server (`task app:build API_URL=https://api.example.com`) and the user can change it on the sign-in screen.

`task app:package` builds and packages for the host OS into `app/dist/<version>/` (`API_URL` works the same). Installers are not cross-built: every platform builds on its own machine (the release workflow has a runner per OS).

| OS | Formats | Tool | Needs |
| --- | --- | --- | --- |
| Linux | `.AppImage`, `.deb`, `.rpm` | Fastforge (DEB), `tool/package/appimage.sh` (AppImage), `tool/package/rpm.sh` (RPM) | `clang cmake ninja-build pkg-config libgtk-3-dev libsecret-1-dev`, `rpm` (rpmbuild), `file`, `appimagetool` on the PATH (set `APPIMAGE_EXTRACT_AND_RUN=1` without FUSE) |
| macOS | `.dmg` | Fastforge | Xcode, `npm install -g appdmg` |
| Windows | `.exe` installer | Fastforge with Inno Setup | Visual Studio C++ workload, Inno Setup 6 (`choco install innosetup`) |

Fastforge is pinned (`dart pub global activate fastforge 0.6.12` runs inside the task). Its configuration lives next to the platform code: `linux/packaging/{appimage,deb}/make_config.yaml`, `macos/packaging/dmg/make_config.yaml`, `windows/packaging/exe/make_config.yaml`. The RPM is built by `tool/package/rpm.sh` from `linux/packaging/rpm/backlog-manager.spec`, because Fastforge's RPM maker does not work with rpm 4.20 and marks the icon setuid.

Decisions (#277):

- **Formats:** DMG for macOS, an Inno Setup `.exe` for Windows (the counterpart of the NSIS installer; a per-user install without administrator rights), AppImage, DEB and RPM for Linux. There is no MSI: Fastforge has no maker for it and the `.exe` covers the same need. MSIX is not offered either, because it cannot be installed without a trusted signature and the app ships unsigned (the same baseline as the Tauri client; the signing decision is #280).
- **Identity:** display name "Backlog Manager", bundle and application id `dev.theocloud.blm` (the id of the Tauri client, so the Flutter client replaces it on macOS and keeps one desktop entry), company "Theo Leuthardt". The binary on disk stays `backlog_manager`.
- **Version:** one source, `version:` in `pubspec.yaml` (`X.Y.Z+build`). `package_info_plus` reads it for the status bar; the release workflow stamps it from the release version and uses the run number as build number.
- **Artifact names:** `Backlog-Manager_<version>_<os>_<arch>.<ext>`, for example `Backlog-Manager_0.9.3_linux_x64.AppImage`, `Backlog-Manager_0.9.3_macos_universal.dmg`, `Backlog-Manager_0.9.3_windows_x64.exe`.
- **Icons:** `tool/icons/icon.svg` is the single source (a ringed planet in the colours of the Shelf theme); `task app:icons` renders the macOS icon set, the Windows `.ico` and the Linux PNG (needs `rsvg-convert` and ImageMagick).
- **Install locations** (what the in-place updater of #279 has to know): DEB puts the app in `/opt/backlog_manager` with a symlink in `/usr/bin`, RPM in `/usr/share/backlog-manager`, an AppImage is the file the user keeps, the DMG holds `backlog_manager.app` for `/Applications` and the Windows installer uses `%LOCALAPPDATA%\Programs\Backlog Manager`.

**The AppImage is assembled by `tool/package/appimage.sh` (#438), not by Fastforge:** Fastforge puts every library `ldd` finds into it, and since the WebKit plugin that was the whole WebKitGTK tree of the Ubuntu build machine (76 MB instead of 19 MB), which does not run on a Fedora based system (v0.9.6 on Bazzite: `libjpeg.so.8` missing, Fedora has `.so.62`; `AppRun` also put the bundled libraries first with `LD_LIBRARY_PATH`). The script copies only the Flutter release bundle (about 11 MB) into an AppDir with a plain `AppRun` and runs `appimagetool`; WebKitGTK 4.1 and libsoup 3 are a requirement of the system like for the deb and rpm. `tool/package/check_appimage.sh` fails when the AppImage holds anything but the bundle and the files of the AppImage itself (it runs in `task app:package` and in the Linux build job of CI).

Verified so far: the three Linux packages are built locally (an AppImage starts under Xvfb); the macOS and Windows packages only run in the release workflow's dry run.

## Release workflow

`.github/workflows/release-app.yml` (manual, "Release Flutter App") builds Linux, macOS and Windows on their own runners, packages with `task app:package` and uploads the installers as workflow artifacts. It keeps the version rule of the former Tauri pipeline (`scripts/release-version.mjs`, tested by `task release:test`): the optional `version` input, otherwise a patch bump of the latest `v*.*.*` tag, and a requested version must be greater than the latest tag. The default server comes from the repository variable `API_URL`.

- **Dry run:** with `publish` off (the default) nothing is released; take the installers from the run's artifacts.
- **Publishing:** `publish` creates the GitHub Release with generated notes and all installers. Since the cutover (#287) a release is a full release by default; `prerelease` marks it as a pre-release, which only the Preview update channel offers (`APP_UPDATES.md`). 0.9.13 was the first full release.
- The release notes start with the install instructions for unsigned builds (`.github/release-install-notes.md`). The builds are not code signed; that is a decision for later (#280).

## Mobile (Android and iOS)

The mobile port is epic #289 (#519-#528). The app id is `dev.theocloud.blm` on every platform; Android needs 8.0 (API 26) or newer, iOS 16 or newer.

- **Run:** `task app:dev:mobile DEVICE=<id>` on a connected device or emulator (`flutter devices` lists them). Against the local backend (`task backend:dev`, the debug default `http://localhost:8000`) run `adb reverse tcp:8000 tcp:8000` first: `localhost` on an Android emulator or a USB device is the device itself, and the reverse forwards it to the backend on the computer. The iOS simulator shares the network of the Mac and needs nothing. A physical iPhone (and an Android device without the USB reverse) cannot reach a local backend: `localhost` is the phone itself, and plain `http` to the computer's LAN address is refused like on the desktop, so point it at an `https` backend (the deployed one or an `https` tunnel to the local one). Plain `http` stays limited to loopback hosts, as on the desktop: `res/xml/network_security_config.xml` allows cleartext only for `localhost`, `127.0.0.1` and `::1`, and iOS allows local networking (`NSAllowsLocalNetworking`).
- **Build:** `task app:build:apk` (debug APK in `build/app/outputs/flutter-apk/`; release builds are unsigned until the release signing of #520) and, on macOS, `task app:build:ios` (release build without code signing, packed by `tool/package/ipa.sh` as `dist/<version>/Backlog-Manager_<version>_ios.ipa`). The IPA is unsigned: the user signs and installs it with a signing tool (KravaSigner); Android ships as a signed APK (#520).
- **Desktop-only plugins:** `window_manager`, `desktop_webview_window` and `desktop_drop` only run where `isDesktopPlatform()` (`lib/platform/desktop.dart`) is true: the window setup in `main.dart`, the window controls of the title bar (`NoWindowControls` on mobile), the browser window (the system browser on mobile) and the file drop of the CSV import. The check reads the real operating system, not `defaultTargetPlatform`, which widget tests report as Android, so the tests keep the desktop behaviour.
- **Trailers:** the embedded player (`flutter_inappwebview`) also runs on Android and iOS.
- **Android Gradle Plugin:** pinned to 8.13 (Gradle 8.14.3, needs a JDK 17 or 21) in `android/settings.gradle.kts`, because `flutter_inappwebview_android` 1.1.3 calls `getDefaultProguardFile('proguard-android.txt')`, which AGP 9 rejects. Flutter warns that its AGP 8 support ends soon: move to AGP 9 (the template's 9.1 and Gradle 9.3) once `flutter_inappwebview` 6.2 is stable.
- **Shell (#521):** `shellLayoutFor` (`lib/shell/shell_layout.dart`, tested) picks the layout. The desktop always keeps its window (title bar, sidebar, inspector pane, status bar), so nothing changes there. On Android and iOS the available size decides:
  - **compact** (narrower than 600, a phone in portrait): `MobileTopBar` with back, page title and the counts of the status bar, and a `BottomNavBar` with Home, Library, Add, Space and More.
  - **medium** (a phone in landscape, the Retroid Pocket 6 and AYN Odin 3, a tablet in portrait): the same top bar and a `ShellNavRail` with the same items.
  - **expanded** (a tablet in landscape, at least 1000x640): the desktop window.
  More opens the whole sidebar (every item, the themes, the account) as a drawer (`NavigationDrawerPanel`). The inspector always fills the screen outside the expanded layout. The main area keeps a `GlobalKey`, so turning the device keeps the page and its state. Safe areas keep the bars clear of the notch, the Dynamic Island and the home indicator. Goldens: `test/shell/goldens/mobile_window_*.png` at 402x874, 874x402, 732x412 and 960x540; tests take the mobile branches with `pumpApp(desktop: false)` (`test/shell/shell_harness.dart`).
- **Pages (#522):** `ShelfFormFactor` (`lib/design/form_factor.dart`) is set above the navigator from the shell layout (compact = a phone in portrait), so sheets and dialogs see it too; the UI kit reads it rather than the screen width, which keeps a narrow desktop window and the component goldens in their desktop form. On a phone in portrait:
  - `ShelfFormRow` puts its control below the label, `showShelfSheet` rises from the bottom over the full width (at most 92 % high, above the keyboard, clear of the home indicator), `ShelfSheetFooter` wraps and drops its Esc hint, and `KeyHint`s are left out.
  - Settings show the list of tabs first and each tab on its own with a way back; with less height (a handheld) the tab list scrolls.
  - Appearance stacks the theme list, the editor and the preview below 960 px.
  - The library's toolbar and filter bar scroll away with the games on every mobile layout; the selection bar stays.
  - **Touch and text size:** `ShelfFormFactor.touch` (any Android/iOS device) gives every `ShelfPressable` a tap area of at least 48x48 dp (the look keeps its size, like Material's padded tap targets), raises fixed control heights with `ShelfFormFactor.heightFor` (inputs, selects, the library search, the segmented control, the filter bar) and sets the input theme to 48 in `app.dart`; text scaled up to 1.3 fits: labels ellipsize, the filter bar compares its width thresholds against the width divided by the text scale, and the sheet footer puts the primary action below when the two do not fit beside each other (`OverflowBar`). `test/features/touch_test.dart` checks `androidTapTargetGuideline` and text scale 1.3 on every page and the main screens with data at phone and handheld size.
  - **Touch interactions (#523):** a long press opens the context menu that a right click opens (`ContextMenuRegion`, with a haptic tick); it holds Open Details, Select (which starts the selection, a tap then toggles games) and Move to status / Categories, which replace drag and drop: dragging games stays on the desktop, because the 250 ms hold that starts a drag would take the long press. Pulling the library down past its top reloads the games (`RefreshIndicator`), and the mobile top bar has a search button for the command palette, which has no shortcut without a keyboard. Tests: `test/features/library/touch_interactions_test.dart`.
  - **Gamepad (#524, Retroid Pocket 6, AYN Odin 3, Bluetooth controllers):** the D-pad moves the focus like the arrow keys and finds the first control when nothing has the focus, A activates like Enter, and `lib/shell/gamepad.dart` maps the other buttons in one place: B goes back (`navigateBack`: an open menu, then the topmost sheet or dialog, then the palette, then the inspector, then the history), X opens the context menu of the focused game, Y the command palette, L1/R1 step through Home, Library and Space, Start opens the settings. `ShellShortcuts` adds them on touch screens only. The system back of Android uses the same `navigateBack` (`SystemBackHandler` around the mobile shell and the pages without a sidebar), so it closes sheets and steps back instead of leaving the app. Tests: `test/shell/gamepad_test.dart`.
  - `test/features/mobile_pages_test.dart` opens every page, the library with games, the creation tool, every inspector tab and the add game sheet with results at 402x874, 874x402, 732x412 and 960x540 and fails on any overflow; goldens of the library, the inspector, settings, appearance and the add game sheet are in `test/features/goldens/mobile_*`.
- **CI:** on every app pull request `app.yml` builds a debug APK (JDK 17, job "App Android Build") and, in parallel, runs `integration_test/mobile_smoke_test.dart` on an Android 14 emulator (job "App Android Smoke Test") (`reactivecircus/android-emulator-runner`, KVM of the GitHub runner): the real app with the real keystore and preferences against the in-memory backend, so a plugin without an Android implementation fails there. It also builds the unsigned IPA on macOS. The APK and the IPA are attached to the run as artifacts (`android-apk`, `ios-ipa`) for a check on a real device. Both Android jobs cache Gradle, the NDK, CMake and the emulator snapshot; GitHub shares a cache made on a pull request only with that pull request, so the two Android jobs also run on every push to `main` that changes the app, and every new pull request starts from those warm caches (the other app jobs run on pull requests only).
- **Testing the mobile layout:** golden tests at the phone (402x874, portrait) and handheld (Retroid Pocket 6, AYN Odin 3, landscape) sizes next to the unchanged desktop goldens, the integration flows in a window of those sizes, the emulator smoke test, and spot checks on the devices with the CI artifacts. There is no local emulator: the development container has no KVM.

## Architecture

The app talks to the backend directly over REST with the JWT as a Bearer token, like the web client, and keeps no database of its own.

```text
features/*  ──►  providers (Riverpod)  ──►  lib/api (Dio + generated client)  ──►  backend
   │                                              ▲
   └──►  design/ (tokens, theme, shared widgets)  └── Bearer interceptor, 401 → sign out
```

- **State:** Riverpod. A provider per backend resource (entries, categories, statuses, user, space), `AsyncNotifier`s for things that change, query keys carry the backlog scope (personal or space) like the web client's hooks. Screens read providers and hold only UI state.
- **Routing:** `go_router` with the same route names as the web app; a redirect guards the routes that need a session.
- **API:** `lib/api/generated/` is the committed output of `task app:generate-api`; hand-written code never edits it. The backend's snake_case JSON is mapped to camelCase fields in the generated models, so screens never see the wire format. Errors become `ApiException` with the message to show.
- **Design:** widgets read colours and sizes from the `ShelfTokens` theme extension, never hard-coded values, so a theme change repaints everything.
- **Logic:** anything that is not about widgets (sorting, filtering, validation) is plain Dart in a file of its own with unit tests; screens call it.

## Theme and design tokens

`lib/design/` turns the six colours of a theme into the whole Shelf palette. `ShelfTokens.forTheme(resolvedTheme)` returns the hand-tuned token set of a built-in theme that has one (`shelfOled`, `light`, `colorful`, `freaky`; `builtin_tokens.dart`, taken from `docs/design/canvas/shelf.css`) and derives the set of every other theme, including `dark` and custom themes, with `ShelfTokens.fromColors` and the formulas of `docs/DESIGN_SYSTEM.md`. `buildShelfTheme(tokens)` creates the `ThemeData` with the tokens and `ShelfTextStyles` as extensions, so widgets use `Theme.of(context).extension<ShelfTokens>()!`.

- The font is Plus Jakarta Sans, bundled in `app/assets/fonts/` (five static weights, SIL Open Font License, `OFL.txt`), so the app looks the same offline.
- Text colours (`foreground`, `text2`, `muted`, `faint`) reach 4.5:1 on the background in every built-in theme and the status colours reach it on the surface; tests in `test/design/` pin that. The light theme's `danger` on its cream background is 4.27:1, just below, which is why the status colours are checked against the surface they are used on.
- The derived colours of a custom theme follow the written formulas, the built-ins use their tuned values; the test compares both with the documented Shelf OLED table.

## Window shell and routing

`lib/shell/` is the frame of the main window: `AppShell` puts the title bar, the sidebar, the main pane with an inspector slot and the status bar over the atmosphere. Pages come from `go_router` (`lib/routing/router.dart`):

| Route | Window |
| --- | --- |

- **Shortcuts** (`shell/shell_shortcuts.dart`): Cmd+S (macOS) or Ctrl+S focuses the search field of the library header, or opens the command palette on a page without it, Cmd+K (macOS) or Ctrl+K opens the command palette (`paletteOpenProvider`, see below), the shortcuts of the registered palette actions work from anywhere, and Esc closes the palette and then the inspector. - **Screens fill the shell** through providers: `shellStatusProvider` (counts and sync state in the status bar), `shellInspectorProvider` (the inspector slot), `navigationCountsProvider` (numbers next to sidebar items) and `addGameRequestProvider` ("Add game" in the sidebar).
- The account row's menu switches the theme (`themeIdProvider`, not stored yet, that is the appearance issue) and logs out.

## Sign-in and session

`lib/auth/` holds the session of the app, `features/auth/` its two pages.

- **Token:** `TokenStore` keeps the access token in the OS secure store (`flutter_secure_storage`: Keychain, Credential Manager, libsecret). On macOS the legacy keychain is used because the data protection keychain needs a signed app with a keychain access group, which comes with the signing issue (#280).
- **State machine:** `AuthController` (`auth_controller.dart`) restores the session at start (`restore`, called from `main.dart`), signs in with a password and, for an account with two-factor, with a 6-digit or backup code (whitespace is removed), signs out and ends an expired session. `LoginFlow` is what the sign-in page shows (step, challenge, busy, error banner); the session itself stays in `SessionNotifier`, which the route guard reads.
- **Revocation and stale answers:** a 401 from any request calls `sessionExpired` (the Dio interceptor of `createApiDio`), which signs out and shows "Your session has ended". Every request remembers the `sessionGenerationProvider` value it started in and is dropped when the user signed out in the meantime, so a slow answer cannot bring the old session back. The generation grows on every sign-in and sign-out; providers that hold the data of a user have to watch it, so nothing of the previous user survives into the next session.
- **Server:** the sign-in page shows the server in use and "Change" opens a sheet that validates the address, asks `GET /health` and signs the user out when the server really changed (`changeServer` of `api/server_url.dart`); `apiDioProvider` is created again for the new server.
- **Not ported on purpose:** the web client's "already signed in" state with "Go to Dashboard" and "Sign out": the route guard sends a signed-in user from sign-in to Home, so that state cannot occur.

## Setup wizard and partial updates

`features/setup/` is the first-run wizard: theme, sorting, Steam, IGDB, done, with a vertical stepper. Every step saves its values when the user presses Next (`SetupController`), a failed save stays on the step with a toast, "Skip setup" and the last step set `setup_completed` and refresh the session user, which makes the route guard lead to Home. A single IGDB field is refused with the message of the web client; the theme applies at once and is saved with the first step.

- **Partial updates:** `PUT /api/user/me` reads an explicit `null` as "clear this field" and leaves omitted fields alone. The generated request classes send every field, nulls included, so one saved setting would wipe the others. Use `UserUpdate` (`auth/user_api.dart`), which only sends the fields that are set, for every partial update of the user, and do the same for the entry updates (`PUT /api/backlog/entries/{id}`). Clearing a field will need an explicit way to send a `null`, to be added with the first screen that needs it (the settings).
- **Links:** `LinkText` writes links inside a paragraph; `urlOpenerProvider` opens them in the system browser and is replaced in tests.

## Entries and Home

`data/backlog_api.dart` wraps the backlog routes (`BacklogApi`, faked in tests) and `data/backlog_providers.dart` holds the state: `entriesProvider(spaceId)` is an `AsyncNotifier` per backlog scope (null is the personal one), dropped when the session generation changes. `moveToStatus` changes the list at once, restores only that entry when the request fails and returns the error message, so the caller decides how to show it. Partial updates go through the map-based `EntryUpdate`.

`features/home/` is the Home screen: four stat tiles, the "Continue playing" hero card (the game in progress with the most playtime, achievements still locked for Steam games, "Open details" and "Mark as completed"), and the shelves "Up next" and "Recently completed" with "See all". The "See all" and cover links open `/library?status=...` and `/library?entry=...`; the library screen reads these parameters. The Home screen reports the number of games to the status bar.

## Library

`features/library/` is the library screen. `domain/library_groups.dart` builds the sections for every sort option (status groups include empty ones and the custom statuses, category groups append categories without games, a status filter limits the status groups); `library_content.dart` feeds it from the entries and watches only the sort option and its direction, so folding a group or paging does not sort again; `library_view.dart` holds the view state (sort, layout, collapsed groups per sort and group, 60-cover pages). The page is one `CustomScrollView` with a header sliver and a grid or list sliver per group, so a library of thousands of games only builds what is on screen. The account's default sort and whether a Steam ID is set come with the session user (`auth/session_user_mapper.dart`).

The IGDB and Steam sync buttons of the toolbar arrive with their features (#268, #269), the filter bar with #261, the selection mode with #262; collapsed groups are kept in memory for the session.

### Filter bar

The 44 px bar under the library toolbar (`features/library/filter_bar.dart`) holds one token per active filter, the dashed "+ Add filter" token, and on the right the owned-only switch, "Reset", the sort menu with its direction button and the grid or list toggle. The filters live in `data/filter_providers.dart` (`filtersProvider`: the search text of the library search field plus the filters; it survives screen changes and starts empty with the next session); `effectiveFiltersProvider` drops selected categories that no longer exist, and `filterOptionsProvider` and `filterBoundsProvider` supply the picker values (the largest value of the data rounded up, at least 10 hours, for the time ranges). The pure part is in `domain/filter_tokens.dart` (`FilterField`, `filterTokens`, `setListFilter`, `setRangeFilter`, `resetFilters`, `filterBounds`) on top of the ported `filterEntries`. The bar adapts to its width: under 900 px it drops the caption of the owned-only switch, under 700 px the sort menu becomes an icon, and under 520 px (the pane of the smallest window, 1000 px, with the details open) it also drops the word "Filter" and the grid and list toggle becomes one icon button (`layout-toggle`), so the tokens keep room for "+ Add filter". The tests of the narrow modes (`test/features/library/filter_bar_narrow_test.dart`) load the real font (`PlusJakartaSans`) with a `FontLoader`: the default test font has square, very wide glyphs and reports overflows that the app does not have.

- "+ Add filter" opens a searchable list of the fields (Category only when categories exist) and then the picker of the chosen field; a click on the text of a token opens the same picker, the x removes the filter.
- A list field is a list of checks; a range has a minimum and a maximum (fields and slider). A range over the whole slider is no filter, and entries without a value are not excluded by a range.
- The library search field filters by title, ignoring case, and does not count as a filter. The status bar shows "N of M games" and, when filters are active, the number of filters; each list filter, each range and owned only count once.

### Custom statuses

Besides the five default statuses (`domain/status_names.dart`, `defaultStatuses`) users create their own, in their personal backlog and, separately, in a shared space. `StatusSelect` (`features/common/status_select.dart`) is the drop-down every place that picks a status uses: the defaults first, the current value of the entry when it is none of the known statuses (a CSV import, for example), then the custom ones each with a delete button, and "Add Status" at the end. That opens a sheet with a name field (at most 20 characters, Enter creates) and live validation from `statusNameError`: "Max 20 characters", "That's already a default status", "You already have a status with that name". Creating selects the new status and shows a toast; deleting the selected status clears the field (`onChanged('')`); entries keep their status text. `customStatusActionsProvider(spaceId)` creates and deletes through `BacklogApi` and reads the list again. The filter options, the library groups and the status order (defaults, custom, then statuses only entries carry) already include the custom statuses. `ShelfSelectTrigger` (the closed state of a drop-down) and `ShelfMenuRow` (a row of a popover list) are shared with `ShelfSelect` and the filter bar.

### Categories

Categories group games independently of their status. `CategoryActions` (`categoryActionsProvider(spaceId)` in `data/backlog_providers.dart`) creates, renames, recolours and deletes them and adds or removes one on a game; after every change the categories and `entryCategoriesProvider` (the map from a game to its categories that sorting, grouping, filtering and the inspector read) are loaded again, so the library follows. A rename sends only the changed fields: the backend rejects a `null` for the name or the colour, which the generated request class would send, so `ApiBacklogApi.updateCategory` builds the body itself.

- `CategoryPicker` (`features/common/category_picker.dart`) is for one game: a chip with a colour dot and an x for each category it has, a "Category" popover (all categories alphabetical and case-insensitive, checkable, plus a "New category" form with the colour, the name and "Create and add"; Enter creates; the default colour is the next of the eight in `categoryColors`) and a "Manage" button. If the category was created but could not be added, the toast says so.
- **Group dots (#429):** in the library the dot of a group of the category sort has the colour of its category (`LibraryGroup.color`, from `buildLibraryGroups(categoryColors:)`), also for categories without a game. The dots of the status groups keep their fixed status colours, and the groups "Uncategorized" and those of the other sorts use the accent of the theme.
- `showCategoryManager` (`features/common/category_manager.dart`) opens the manage sheet: one row per category with a colour picker and a name field, saved on Enter or when the field loses focus (a failed save resets the row), delete behind a confirmation that the category is removed from every game that uses it.
- `ShelfColorPicker` is a swatch with a popover of the palette and a `#rrggbb` field. Inside another popover (the category popover) the swatch and the palette are used inline (`ShelfColorSwatch`, `ShelfColorPalette`): a tap in a nested popover would close the outer one.
- The name rules are the ported `categoryNameError` (at most 100 characters, duplicates rejected case-insensitively with the message of the web client).

### Selection, bulk actions and the context menu

`selectionProvider` (`data/selection_providers.dart`) holds whether the library is in selection mode and which games are selected; it stays while the user moves between screens and starts empty with the next session. The "Select" button of the toolbar turns the mode on and the toolbar is replaced by the accent-tinted `SelectionBar` (`features/library/selection_bar.dart`): "N selected", "Select all N" (every game that passes the filters and the search), Clear, a "Set status" menu, a "Categories" menu, Delete and Done. In selection mode a click toggles a cover and the covers show their check circle; outside it a click opens the details of the game (`/library?entry=<id>`, which the inspector will read). The status bar shows "N of M games selected".

- Bulk set status, bulk delete and the bulk categories send one request per game, at most eight at a time (`runBulk`), and report "Moved n games to X", "Moved n to X, m failed", "Deleted n games", "Deleted n, m failed", "Added n games to \"X\"" and "Removed n games from \"X\"" (`domain/bulk_messages.dart`). Deleting asks first ("Delete n games?", "This action cannot be undone."). The bulk categories menu is new compared to the web client: a category that all selected games have is checked, and choosing it removes it from all of them, otherwise it is added to all.
- The context menu (right click on a cover or a row) has the title of the game, Open details, Select, Move to status (the current status is disabled; the toast offers Undo), Categories (checkable, stays open, disabled without categories) and Delete.
- Keyboard: Enter or Space activates a focused game (opens it, or toggles it while selecting), Backspace or Delete asks to delete it (the whole selection when the game is part of one), the arrow keys move the focus to the neighbouring game.
- `LibraryActions` (`features/library/library_actions.dart`) is created by the library page and handed down with `LibraryActionsScope`: a game that moves to another status group is built again, so its own context and ref cannot be used for a toast or an Undo that comes later.

### Drag and drop

In the status sort a game can be dragged onto another status group, in the category sort onto a category group (`features/library/entry_drag.dart`, pure logic in `domain/drag_drop.dart`). A mouse or stylus starts the drag after 8 px, a finger after a 250 ms hold (`_EntryDragRecognizer`), so a click still opens the game and touch scrolling keeps working. There is one drag per page, run by `LibraryDrag`: it finds the group under the pointer from the group headers that are on screen (`groupIndexAt`), so the whole group, its gaps and its empty body take the drop, highlights it (`dragProvider`) and scrolls while the pointer is within 72 px of the top or bottom edge (`edgeScrollVelocity`).

- Status sort: dropping on the group the game is in does nothing; otherwise the status changes and the toast "Moved <title> to <status>" offers Undo.
- Category sort: the target category is added and the first category removed (`categoryMove`); dropping on the first category does nothing, "Uncategorized" is no drop target and empty categories stay visible and take a drop. An empty group shows a dashed hint while a game is dragged.
- Dragging is off in every other sort option and in selection mode, where a click toggles a game and a drag would only get in the way.

### Not Owned and the owned flag (#382)

"Not Owned" is the sixth built-in status (`notOwnedStatus`, `defaultStatuses`), so it is in the status menu, the filter and always a group to drop a game on, and it cannot be created as a custom status. It goes with the owned flag, and the server keeps the two in step when only one of them is sent (`services/entry_ownership.py`, used by `PUT /api/backlog/entries/{id}`, which every client and bulk action goes through): a game moved to "Not Owned" is marked not owned, a game moved out of it is marked owned, a game marked not owned moves to "Not Owned", and a "Not Owned" game marked owned starts ("Not Started"). A request that sets both is kept as sent, and the Steam and CSV imports set both themselves. `BacklogEntry.withStatus` mirrors the first two rules for the optimistic move of a dragged card. The completion date does not need this: a database trigger owns it.

**Mods (#409).** Every game has a list of mods, each a name (up to 120 characters) and an optional http(s) link: the "Mods" tab of the inspector (`features/inspector/mods_section.dart`, logic in `domain/entry_mod.dart`, state in `data/entry_mod_providers.dart`) lists them, opens a link in the browser, adds ("Add mod" sheet), edits and removes them, each change saved at once. The server keeps them in `BacklogEntryMods` (`GET/POST /api/backlog/entries/{id}/mods`, `PUT/DELETE .../mods/{mod_id}`, at most 100 per entry, anything but http(s) links is refused). They belong to the entry: in a shared space both members see and change the same list, and they are part of the personal backups (`BackupEntry.mods`, older snapshots restore without). Copying a game to the space does not copy its mods.

**In a shared space (#413)** ownership belongs to each member: `SpaceEntryMemberData.Owned` next to playtime, rating and review, filled for the creator when an entry is created, and `GET`/`PUT` with `space_id` read and write the caller's own flag (a member who never set it counts as not owning the game; the migration copied the entry's old flag to every active member). The status stays shared, so there is no coupling with "Not Owned" there (`withStatus(ownershipFollows: false)` for the optimistic move), and "Owned Only" filters by the member's own flag.

### Random pull (#383)

The dice button in the library toolbar (key `random-pull-button`, next to "Find duplicate games") and the palette action "Pull a random game" open the **Random Pull** sheet (`features/random_pull/random_pull_sheet.dart`, request counter `randomPullRequestProvider`, handled by `PaletteHost`). It picks one game at random from the games the library shows, so the filters and the search text narrow the choice (`libraryContentProvider`); with no filter that is the whole backlog. The pure logic is in `domain/random_pull.dart`: `pullCandidates` keeps the games the user owns and, unless the switch "Include finished games" is on, leaves out Completed and Dropped; a game that is not owned (a wishlist game) is never pulled. `pickRandom` never gives the game that was just pulled again when another one is there. The sheet shows the cover, title, `status · hours` and genres and platforms, how many games it chooses from, "Pull Again" (not offered for a pool of one) and "Open Details", which closes the sheet and opens the game in the library (`/library?entry=<id>`, like the palette). The source of the randomness is `randomProvider`, so tests pass a fixed sequence. With no game in the pool the sheet says "No game to pull".

**On the Home page (#455)** a bar under the stat tiles ("Can't decide what to play next?", key `home-random-pull`, button "Random Pull") opens the same sheet, through `randomPullRequestProvider` like the library button and the palette; the library keeps its own dice button. The bar is not shown while the backlog is empty.

**Groups and the slot machine (#445).** The dice button no longer pulls at once: the sheet first lists the groups the library is currently sorted by (status, category, genre, ... as `libraryContentProvider` groups them, with the category colour dot) as checkboxes with the number of games each group offers ("All" and "None" at the top, every group is in by default, "Include finished games" lives here too). A group that is left out takes its games out of the pull (`pullPool` in `domain/random_pull.dart`, `groupPullCount` for the counts); with nothing left "Pull" is disabled and the sheet says "No game to pull". "Pull" picks the game (`pickRandom` with `randomProvider`, as before) and then a slot machine reel (`features/random_pull/slot_reel.dart`, `SlotReel`) runs through every game of the pool once, shuffled (`reelStrip`, the games of the groups that were chosen, so a pool of 200 games has 200 rows before the stop; the rows are built lazily, only the ones in the window, so covers are loaded only for those), ending on the pulled game.

A pool with fewer than 30 games is repeated in front by whole rounds so every game is on the reel equally often, and 3 more games follow the pulled one so the reel looks as if it could have stopped anywhere (the strip is drawn with its own seeded `Random`, so the reel never consumes `randomProvider` and tests keep their fixed sequences) in a window of three rows and stops after 5 seconds (`slotReelDuration`, made longer in #448 for more suspense) with the pulled game on the highlighted middle row. A metal arrow (drawn, `_PointerPainter`) sits at the right edge pointing at that row and throws sparks while the reel runs past it; their strength follows the speed of the reel (`reelSparks`: full while it is fast, gone before it stops); then the result appears with "Change groups" (back to the list, the choice is kept while the sheet is open), "Pull Again" (spins again, not offered for a pool of one) and "Open Details". With the system setting "reduce motion" there is no reel and the result shows at once. Deliberate change of behaviour: the sheet used to show a game as soon as it opened and "Include finished games" pulled again; both tests moved to the new first step.

**In the Shared Space (#424)** the header of the space has the same dice button (`random-pull-button`) and the palette action works there too. The pool is the games of the space as the library shows them: the games the user owns (ownership is per member since #413, so a game only the partner owns is not pulled) and still has to play. The sheet says "One game of your Shared Space ..." and "Open Details" opens the game on `/space?entry=<id>` instead of the personal library (`backlogScopeProvider` tells which one).

### The list layout in a narrow pane (#393)

A row of the list (`_Row` in `features/library/library_page.dart`) leaves out the genre and narrows the playtime column below 480 px of row width, so the title and the status keep their room; `ShelfChip` cuts its label with an ellipsis in a space that is too narrow, which also protects its other uses. The tests (`list_layout_narrow_test.dart`, `chip_width_test.dart`) measure at the smallest window with the details open and load the real font with `loadAppFont()` (`test/support/app_font.dart`).

### Ordering the groups

Every group header has a grip: dragging it onto another header moves the group there (`domain/group_order.dart`: `moveGroup` puts the group where the target was, like a reorderable list; `applyGroupOrder` sorts the groups of the current sort by the saved keys and puts groups the order does not know yet after the known ones). It works in every sort option, because group keys carry their sort option (`status:Playing`, `genre:RPG`), so one saved list serves all of them; the order replaces the default and the sort direction only orders the games inside the groups. Screen readers get "Move group up/down" actions on the header. The order is kept on the device (`data/group_order_store.dart`, key `blm-group-order`), not in the account, because the backend has no field for it. This drag is separate from dragging games onto a group.

### Command palette

Cmd+K (macOS) or Ctrl+K opens the palette from any screen of a signed-in session (`features/palette/command_palette.dart`; Cmd/Ctrl+S focuses the search field of the library, and opens this palette on a page without it). `PaletteHost` sits in both window frames: it opens the sheet when `paletteOpenProvider` turns on and registers the actions of the window. The sheet has an input, the section "Games" (the best matches of the loaded entries, a cover thumbnail, title and `Status · 18 of 22 h`) and the section "Actions"; the arrow keys move the highlight, Enter runs it (a game opens in the library with its details, `?entry=<id>`), Esc closes it. Without a query only the actions show.

- Ranking is `fuzzyScore` in `domain/palette_search.dart`: a prefix beats the start of a later word, that beats any substring, that beats the letters in order with gaps; shorter titles first, then by title. At most six games.
- Actions live in the registry `paletteRegistryProvider` (`shell/palette_registry.dart`). A feature registers its action with a stable id (`PaletteAction`, label, `run`, optional `PaletteShortcut`); the same id replaces it in place. `ShellShortcuts` binds the shortcut of every registered action, and the palette shows the same shortcut as its hint (`⌘⇧S` on macOS, `Ctrl+Shift+S` elsewhere), so hints and keys cannot differ. The window registers Add game (Cmd/Ctrl+N), Open settings (Cmd/Ctrl+,), "Go to" for every screen and "Switch theme to" for every built-in theme (`registerShellPaletteActions`). "Sync Steam playtimes" (Cmd/Ctrl+Shift+S) and "Sync IGDB game data" (Cmd/Ctrl+Shift+I) are registered by #268 and #269.

### Prices and achievements

Two reusable sheets for the Steam data of a game; the inspector (#264) and the creation tool (#266) open them.

- The **Prices** button of the inspector (`inspector-prices`) opens Keyforsteam for the game in a browser window of its own (`platform/browser_window.dart`, `browserWindowOpenerProvider`): the catalog searched for the title, `https://www.keyforsteam.de/katalog/?search_name=<title>` (`keyforsteamSearchUrl`, what the search form of the site sends; the `SearchAction` address `/katalog/search-<term>` only shows the empty catalog), which lists the offers. The window is the system web view (WebKitGTK 4.1, WebView2, WKWebView, package `desktop_webview_window`) with the title bar of the plugin (back, forward, reload, title). Only https pages of keyforsteam.de and its subdomains load there (`staysOnKeyforsteam`, checked for every navigation); everything else, the shops the offers lead to included, opens in the system browser. On Windows the WebView2 profile lives in `%LOCALAPPDATA%\\Backlog Manager\\WebView2` (the default next to the executable fails in a folder that is not writable). No JavaScript handler is registered, so the pages cannot reach the app. A second click closes the first window. Without a web view (Windows without the WebView2 runtime) or when the window cannot be created, the address opens in the system browser. The GG.deals price sheet and the key shop list of the app were replaced by this window (#421), and the price tracking behind them (GG.deals client, price cache, Discord price alerts, key shop scrapers, their routes and settings) was removed completely in #436. **Linux:** the plugin links `libwebkit2gtk-4.1` and libsoup 3, so a system without them cannot start the app at all: the deb and the rpm declare them, the AppImage does not bundle them (release notes say so), and the build and release jobs install the dev packages.
- `AchievementProgressSection(steamAppId:)` (`features/achievements/achievement_progress.dart`) shows `3/15 (20%)` with a progress bar and "Show all achievements", which opens `AchievementsSheet` (icon, name, description or "Hidden achievement", the locked ones dimmed). It shows nothing without a Steam App ID, without achievements and when the request fails.
- `data/game_info_providers.dart` caches the answers: achievements for five minutes (an auto-dispose provider kept alive for the time to live; the times are providers so tests can shorten them).

### Entry inspector

`/library?entry=<id>` opens the inspector of a game in the 380 px slot on the right of the main pane, with the list kept visible (`features/inspector/`). `AppShell` reads the `entry` of the address and puts `EntryInspector` into `shellInspectorProvider`; the close button and Esc take the game from the address again, and a game that does not exist (any more) closes it. The form is built from the stored entry every time the inspector opens.

- Header: "Details" with the save state and a close button; cover, title, "Genre · Platform" line, "Completed on <month year>", the status select with the status colour, the category chips with "+ Category" (`CategoryPicker`), "Prices" (Keyforsteam in a browser window) and "Update image" (an http(s) address, applied with Enter).
- Stat tiles: playtime in hours (the partner's as "Your partner: Nh" in the shared space), interest as the numbers 1 to 10 (`InterestPicker`, see below) and ownership ("In my library" / "Not owned").
- Tabs: Overview (genre and platform as fields, the description), Progress (HowLongToBeat bars against the playtime, then the achievements), Notes (the note, a text area of its own since #428), Review (stars and review text only for the status Completed, otherwise "Set the status to Completed to write a review"), Mods and Trailer (a play card that plays the YouTube video, "No trailer available for this game." otherwise). The tabs share the full width of the inspector (`ShelfTabs(expand: true)`). Footer: Delete with the usual confirmation.
- Interest (`InterestPicker`, #428): the numbers 1 to 10 in a row, the ones up to the value filled and the current one ringed; a tap sets the number, the current one is not cleared (an entry always has 1 to 10, clearing sent 0, which the server refuses), the arrow keys step by one. The creation tool and the gallery use it too.
- Autosave (`EntryAutosave`): the fields that differ from the stored entry (`diffEntryForm`: the title of the heading, image link, playtime, genre, platform, status, owned, interest, review stars, review, note) are saved 800 ms after the last change; edits during a running save are saved by the next one; closing saves what is pending; a failed save shows "Not saved" and a toast. Description and times change only through "wrong game", which also replaces the title.
- When the stored entry changes while the inspector is open (a drag to another group, a sync) the fields the user has not touched follow it (`rebaseForm`), so the autosave never writes the old value back and the inspector stays open when the game moves between groups.
- Footer: Delete, "Wrong game?" and "Change cover" (the sheets below). Not here yet: "synced 2 h ago" (#268). The trailer plays in a sheet (see "Trailer player").

The **title** is edited right where it is shown, in the heading of the details (#399): a click on it or on the pencil next to it turns it into a text field at the same spot (`inspector-title-input`, selected and focused); Enter or leaving the field keeps the edit and the same autosave saves it (`EntryForm.title`, `EntryFormChanges.title`, trimmed), Esc discards it, and a blank title is never kept (the stored one comes back; while it is blank the field says "A game needs a title"). There is no separate title field in the Overview tab. The heading follows the stored title. The IGDB sync only cleans trademark symbols from a title, it never replaces it, so a rename stays.

The Platform field of the Overview tab has a **Manage** link (`inspector-platform-manage`) that opens "Manage Platforms" (`features/inspector/manage_platforms_sheet.dart`, logic in `domain/platform_choices.dart`): a chip per platform, a tap selects or deselects it, the selected ones first when the sheet opens (the order then stays while you tap), then the platforms of the whole backlog (`filterOptionsProvider`) and the common ones (PC, PS5, PS4, Xbox Series X|S, Xbox One, Switch, Steam Deck, Mobile), each once whatever its case; a field adds a platform of its own (no comma, since the field is a comma-separated list). "Done" applies what you added and removed to the platforms the game has by then (`applyPlatformChanges`), so a change that came in while the sheet was open is kept, and writes it into the field, so the same autosave saves it; "Cancel" changes nothing. The text field itself stays for a quick edit.

### Trailer player

Decision (#351, replaces the browser-only decision of #325): "Watch trailer" opens a sheet (`features/inspector/trailer_sheet.dart`) with the player, like the old Tauri client. The player is `flutter_inappwebview` (WKWebView on macOS, WebView2 on Windows); it has no Linux implementation, so there the trailer plays in a window of its own (see "Linux (#423)" below). `platform/trailer_player.dart` holds the builder behind `trailerPlayerBuilderProvider` (it returns `null` where there is no player, and tests override it), so nothing else knows about the plugin. YouTube refuses some embeds without a referrer, so the sheet always has the "Watch it on YouTube" link.

`domain/trailer.dart` (`youtubeEmbedUrl`) accepts only canonical YouTube watch URLs, and the inspector opens the sheet only after a link passed, so nothing else can ever become the source of the web view.

**Linux (#423):** the trailer plays in a window of its own (`platform/trailer_window.dart`, `trailerWindowOpenerProvider`, the browser window of the Keyforsteam button with WebKitGTK from `desktop_webview_window`, see "Prices"), because `flutter_inappwebview` has no stable Linux implementation (researched in #355: its WPE package is beta and needs `libwpewebkit-2.0-dev`). The window can only be told an address, and YouTube only plays an embed in a page that has an origin (a top-level embed and a `file://` page both give error 153, the full watch page shows the cookie dialog of youtube.com). So `TrailerPageServer` serves the same page as the other platforms (`trailerPage`, with `origin` set to its own address) from the loopback address: `http://127.0.0.1:<port>/<secret>/<video id>`, a random port, a secret of 16 random bytes in the path, only a GET for a well formed video id, started with the first trailer and stopped with the app. The window stays on that page and on the player frame inside it (`stays` is `TrailerPageServer.owns` or the YouTube embed of the video or a non-http frame such as `about:blank`): the window reports the navigation of the player iframe to the same callback as a page navigation, so refusing the embed left the window black and opened it in the system browser without an origin, which is YouTube error 153 (#442, found with a spike under Xvfb). "Watch on YouTube" and every other link open in the system browser. If the server or the window fails, the video opens on YouTube in the system browser. Checked by hand under Xvfb with WebKitGTK 2.54: the player page of a video loads from the Dart server; whether sound and picture play depends on the GStreamer plugins of the system, which the sandbox did not have.

### Settings

`/settings` (`features/settings/`) is a full window: a list of tabs on the left with the account at its foot and the settings of the tab in groups of rows on the right (`/settings?tab=integrations` opens a tab). General (who is signed in, the default sort with all seven options, a link to the appearance screen), Security, Integrations, Backups, Updates (the app updates: check, install, channel; its own tab since #430) and About (version and source link).

- Settings save themselves, there is no Save button: text settings (Steam ID, Steam Family IDs) save 800 ms after the last key, choices (default sort, the wishlist sync) at once. The bottom line shows "Saving...", "Saved" or "Not saved"; successes of secrets and choices also show a toast, and the message of the backend is kept when it refuses a value.
- Security: "Enable Two-Factor Authentication" opens the setup sheet (`features/settings/two_factor_sheets.dart`, API in `auth/two_factor_api.dart`): the QR code of the otpauth address (`qr_flutter`), the key to type in ("Can't scan it? "Disable Two-Factor Authentication" asks for the password and says the backup codes stop working. The account is read again afterwards.

Restore asks first and names the date and the content, says that the current state is saved as a backup, and afterwards reloads the games, categories and statuses; Delete asks first; Download goes through the save dialog of the system (`file_selector`, `platform/file_saver.dart`) as `backlog-backup-<id>.json`.
- "Sync wishlist hourly" is the switch of the automatic wishlist sync (#317). It stays off limits until the first wishlist import has happened (`steam_wishlist_imported_at`).
- Every save goes through `SettingsController` (`PUT /api/user/me` with the fields that changed, `UserUpdate`, then the account is read again). `SessionUser` carries the Steam ID, the family IDs, which secrets are set (never their values) and the wishlist sync fields.

### IGDB sync

"Sync IGDB" in the library toolbar (or "Sync IGDB game data", Cmd/Ctrl+Shift+I, in the command palette) opens `features/igdb_sync/igdb_sync_sheet.dart`. It explains that every game missing a genre or description is looked up and that values the user entered are never overwritten, and counts the games (`GET /api/igdb-sync/pending-count`): "n games will be looked up.", "Every game already has IGDB data." (Start sync disabled) or "Could not count the games to sync.". Start sync reads `POST /api/igdb-sync/stream` through `openSse` (`data/igdb_sync_api.dart`): a progress bar with "Looking up games n/m", the sheet cannot be closed while it runs (`PopScope`, Cancel disabled), and the result is a toast ("Updated n games with IGDB data" or "No IGDB data could be added"), the sheet closes and the entries are loaded again. ### CSV import

`/import` (`features/import_csv/`, logic in `domain/csv_import.dart`, requests in `data/csv_import_api.dart`, state in `csv_import_controller.dart`) imports a backlog from a CSV file in four steps: choose the file (the open dialog of the system, `platform/csv_file_picker.dart`, or drop a `.csv` file on the window with `desktop_drop`), map the columns, preview, import.

- The file is read as UTF-8 text by `decodeCsvFile`: only `.csv`, not empty, at most 10 MB (what the server accepts), a leading byte order mark is dropped; anything else is a toast with the reason. `POST /api/csv/headers` returns the header of every column by its letter.
- Column mapping (360 px group on the left): Title, Genre, Platform, Status (defaults A to D), optional Playtime, Rating and Completed date, and two groups of check boxes: review columns (merged into the review) and note columns (merged as "Header: Value"). "Preview import" streams `POST /api/csv/preview/stream` with "Loading n/m..."; Cancel stops the stream ("Preview cancelled"), an empty result says "No rows with a title found to preview".
- The preview is a lazily built list (`ListView.builder`), and every row watches only its own `csvRowProvider`, so editing one row of a thousand rebuilds that row only. A row shows cover, title, "genre · platform · status", a result chip (Owned, Check match, No beat times, No cover; the first that applies) and a button (Wrong game for a row that was not matched, otherwise Cover), an info line (playtime, rating n/10, completed month, note, review, "No cover found", "No beat times found") and, when the game is already in the backlog, an expandable "Already in your backlog (n)" with the field diff of what the import would change. Tapping the title opens "Edit row": title, genre, platforms (comma separated), status, owned, Wrong game, Choose cover and "Remove from import". Wrong game replaces title, genre (only if the game has some), cover, description, trailer and the three times and marks the row matched (`applyWrongGame`).
- "Import n games" streams `POST /api/csv/submit/stream` ("Importing n/m..."), Cancel says "Import cancelled". The result toast names the created and skipped rows, the entries are loaded again, and the rows the server skipped stay on the start screen as a collapsible "n rows skipped during import" list with title and reason. The server takes a backup before every import and an import never writes to a shared space.

### Shared Space

`/space` (`features/space/`, state in `data/space_api.dart`, logic in `domain/space.dart`) is the shared backlog of two users. `GET /api/space` decides what the page shows: without a space "Start a Shared Space" with the invitation form (username of the partner), with an invitation "<name> invited you to a Shared Space" with Accept and Decline (decline is the leave call), and for an active member the library of the space. The space is read again every 30 seconds while the window is visible (a failed read keeps the screen); leaving or declining invalidates every cached provider of the space, and the sidebar entry gets a dot while an invitation waits.

- **Scope.** `backlogScopeProvider` (`data/backlog_scope.dart`) is the id of the space on `/space` and null on every other page; the router writes the current path into `currentPathProvider` in its redirect. The library, the filters, the selection bar, drag and drop, the status select, the category picker and the inspector all read it, so `/space` renders the regular `LibraryPage` and `/space?entry=7` opens the inspector of a space game. Home, export and import stay on the personal backlog (the IGDB sync follows the page since #431).
- **Header.** Avatars with the initials of both members, "Co-op backlog", "Space Info" (popover, it says that ratings and playtime stay your own), "Leave" (or "Cancel Invitation" while the partner has not accepted) behind a confirmation with the warning that the games stay with the partner, the search field in the middle and "+ Add game" at the far right, exactly the layout of the library header (#431: one `_Toolbar`, the heading is the only difference; the search sits beside the heading from 930 px of width, below that it is stacked like in the library). Under it the tools of the library: Select, Steam sync (with a Steam ID), Sync IGDB, random pull and Find duplicates, each working on the games of the space. The Steam sync syncs the playtime of both members: the server reads the partner's library by their Steam ID with the key of the request (`sync_partner_space_playtimes`; no Steam ID, an invitation that is not accepted or a private library is skipped), and the app reads the entries of the space again. `GET /api/igdb-sync/pending-count` and `POST /api/igdb-sync/stream` take `space_id` (404 for a non-member). While no partner is active an invitation form or "Waiting for alex to accept your invitation." sits under the header. Covers show one bar per member with the initials and hours (`MemberProgress`, the `footer` of `ShelfCover`); "Wrong game?" is not offered in the space.
- **Backups (#444).** The "Space backups" icon button (history icon) sits in the toolbar of the space next to the dice and the duplicates button and opens `SpaceBackupsSheet` (`features/space/space_backups_sheet.dart`, state in `data/space_backups_api.dart`, logic in `domain/space_backups.dart`): "Back up now", "Export JSON" (`GET /api/space/export`), and a row per backup (automatic, manual with the member who took it, safety) with Restore, Rename, Download and Delete. Restore never runs at once while the partner is in the space: a confirmation says that the partner has to approve (button "Ask <name>"), after that the sheet shows "Waiting for <name> to approve restoring ..." with Withdraw. The partner sees "<name> wants to restore ..." with Approve and Decline (also the time left; a request lapses after 24 hours) and a dot on the toolbar button; Approve reloads the entries, categories and statuses of the space. A space with one active member restores at once. While a request is open the Restore buttons are disabled. `spaceBackupsProvider` reads the list again every 30 seconds (like `spaceProvider`), which is how the partner's request shows up. Backend and rules: [`BACKUPS.md`](BACKUPS.md).
- **Adding.** "Add Game" (also Cmd/Ctrl+N) on `/space` opens the search with the space as target (`target=space`); the creation tool has an "Add to" select (My Backlog / Shared Space) when the user has an active space, takes every game, with or without Steam App ID, checks duplicates in the space and returns to `/space`. The inspector of a personal game has "Add to shared space" (copies every field) which becomes "In shared space" and links to the space.

### Appearance and themes

`/appearance` (`features/appearance/`) lists the built-in themes (Shelf OLED, Light, Colorful, Freaky and Classic dark, the old `dark` theme with its id), the custom themes of the account with edit and delete, and a form with the name (30 characters), "Start from" a built-in theme and the six colours (colour picker plus a hex field that shows "Use a colour like #1a2b3c" for an invalid value) next to a miniature preview. ### Test round of #284 (#351)

The first test on a real desktop (macOS) led to a round of changes; the decisions that are not obvious from the code:

- **macOS sandbox:** the file panels (CSV import and export) need `com.apple.security.files.user-selected.read-write` in both entitlement files; without it the open and save panels never appear and the export waits forever.
- **Size and feel:** type scale, control and input heights were raised (see `docs/DESIGN_SYSTEM.md`, "Scale-up"); buttons ease between their looks and shrink on press, covers lift on hover, pages fade in (`_FadeIn` in the router, not a route transition: two pages must never be alive together), the sky twinkles and a moon travels each orbit ring (`atmosphereMotion`, off in tests and with reduced motion).
- **Sign-in** follows the design: a 480 px card with the eyebrow, hero title, 44 px fields and a full-width primary button; the title bar content is centred vertically (it sat at the top before).
- **Library:** the toolbar groups the actions next to the title (an icon button for the IGDB sync with a bolt, a different icon for the duplicates), the Add button is at the right end; a game opened by a search or a click is scrolled to, its group is opened and its cover outlined for two seconds (`reveal_entry.dart`; the page moves one viewport per frame until the lazily built tile exists).
- **Inspector:** "Wrong game?", "Change cover" and "Image link" sit under the status select; the footer only has Delete.
- **Sidebar:** the themes are swatches under "Personalise" with a plus for the creator; the account menu only has Settings and Log out. The sidebar and the inspector can be dragged to another width (`shell/pane_widths.dart`, a double click restores it).
- **Settings** has a "Back to Dashboard" button, and the sidebar toggle of the title bar hides the tab list there.
- **Steam preview** shows what it is doing (`_LoadingPanel`): which list is read, a sweeping bar until the number of games is known, the count and the seconds elapsed.
- **IGDB errors:** the backend answers 503 "IGDB rejected the configured credentials" when Twitch refuses the token request (it was an unexplained 500).
- Cancel buttons of sheets are red; explanations are `ShelfNote`s.

Second round of the same test:

- **Atmosphere:** the sky is a seeded random arrangement of stars (no grid), with drifting dust in three depths, breathing nebulae, twinkling stars and shooting stars on every theme (`AtmosphereMotionPainter`). Settings > General has the switch "Animated background" (`backgroundMotionProvider`, kept on the device); the system setting "reduce motion" turns it off too. The nebulae are ovals with an elliptical gradient shader and the canvas is never scaled for them: with a non-uniformly scaled canvas some Linux GPU drivers (AppImage on Bazzite, #414) filled the whole bounding box with hard-edged squares. That was only a guess: the squares of #440 (reproduced under Xvfb with Impeller GLES) are the bounding boxes of the large stroked circles, so the orbit rings and the pulse ring are drawn as closed polygons of short segments (`_circleOutline`; a stroked `drawCircle`, a stroked path and a filled ring all showed the boxes). Tests switch it off globally with `atmosphereMotion = false` in `test/flutter_test_config.dart`.
- **Brand mark:** the icon next to "Backlog Manager" in the sidebar animates (`design/brand_mark.dart`) under the same switch.
- **Inspector:** the status dot and drop-down sit at the bottom edge of the cover, all actions under the cover wrap in one group, the trailer card spans the sidebar, and the header has a button for the full-screen view (`inspectorFullscreenProvider`) with a button back to the dashboard. The sidebar closes whenever the route is none of Library, Shared space or Home.
- **Motion:** sidebar items glow, slide and light up their marker on hover; the segmented controls slide their thumb (the grid/list switch and the Steam Library/Wishlist switch fade the content); tab underlines grow; grid items fade up; toasts enter.
- **Settings:** the back button reads "Back to Dashboard"; the input fields and their Remove buttons of Integrations share one 110 px trailing slot so they align.
- **Interest bar:** segments are 28 px high to hit, 9 px visible.

Third round:

- **Titles:** two-word titles, labels and buttons are written in Title Case ("Shared Space", "Add Game", "Space Info"); prepositions stay small ("Add to").
- **Space info** is a card (who shares, what is shared by both, what stays one's own), not a grey line.
- **Inspector:** genre and platform are labelled chip rows beside the cover; the partner's playtime is a field-like row under one's own; the full-screen view puts the facts and controls in a 460 px column on the left and the tabs on the right (`_InspectorLayout`), and the shell keeps the inspector's state while it moves between the slot and the full-screen view (`GlobalKey`).
- **Trailer on macOS:** the web view loads a small page with the embed in a frame (`trailerPage`) whose base URL and `origin` are the app id as an https address (`trailerOrigin`, `https://dev.theocloud.blm`). YouTube identifies the embedding client by that origin: a top-level address or no origin gives error 153, a page that claims to be youtube.com gives error 152.
- **Inspector header:** the cover is 132 px wide in the slot (160 in the full-screen view); genre chips fill at most two lines and platform chips one, the rest is a "+N" chip that opens a popover with all of them (`FactChips`, widths measured with the chip's own text style), so the block never gets taller than the cover; in the full-screen view they all wrap. The status drop-down is a full-width row under the header.
- **Shortcuts:** the sidebar entry under Personalise opens `features/shortcuts/shortcuts_sheet.dart`, the list of every shortcut (palette actions come from the registry).
- **Sign-in:** the heading reads "Backlog Manager" in the page size beside a 46 px animated mark; password fields have a show/hide button (`ShelfField.obscure`).
- **Covers while jumping:** a cover requests its image only after it has stayed built for 150 ms (`coverImageDelay`, zero in tests), and the images are decoded at most 420 px wide. Jumping to a game far down a library of 1,300 entries builds the covers of every viewport on the way for a single frame; without the delay each of them queued a download that nothing waited for and the covers on screen appeared after half a minute.
- **Jumping to a game:** the page puts the group header at the top, estimates the row of the game from the grid metrics (`coverGridMetrics`) and jumps there at once; stepping a viewport at a time is only the fallback (the list layout). Typing in the search field of the title bar on a page that is not the library or the Shared Space takes the user to the library.
- **Cover glow:** `design/cover_glow.dart` lights the area around the cover of the inspector in the colour of the cover; the title, the chips and the rest of the panel stay dark. `CoverGlowScope` holds the colour (the saturation-weighted average of the cover scaled down to 24 px, `glowColorFromPixels`, pushed to a bright shade, cached per image, faded in; the theme's own glow until it is known or without a cover), `CoverGlowBackdrop` paints a veil and two soft lights that drift slowly around the cover only, fading out towards the edge of its box (a 20 s loop; the veil sways and breathes as well), `CoverGlowHalo` lights the cover itself. Settings > General > "Animated Glow" (`glowMotionProvider`, kept on the device) and the system setting for less motion stop the drift; the lights then stay where they are. Tests switch all motion off with `atmosphereMotion = false`.
- **Search for a game and Wrong Game:** both sheets use `gameResultColumns` (`features/add_game/game_result_parts.dart`): the sheet is 980 px wide (`ShelfSheetWidth.extraWide`), the thumbnails are 58 x 87 and long platform and genre lists wrap; `ShelfDataTable` rows are at least 48 px and grow with their content.
- **Filter bar:** below 900 px it drops the caption of the owned-only switch, below 700 px also its "Filter" label and the sort menu becomes an icon.

### Publisher

`BacklogEntry.publisher` (from `publisher` of the entry, #293): the creation tool sends the one of the search result and shows it as a "Publisher" block under the cover, like "About"; the "Wrong Game?" replacement carries the one of the chosen game (`WrongGameChanges.publisher`, `EntryUpdate`); the inspector has a "Publisher" field in the Overview tab below Platform, saved with the other edits (`EntryForm.publisher`). Entries stay without a publisher until an IGDB sync, a replacement or an edit fills it; the sync never overwrites a value the user set. The IGDB `companies` request asks only for fields the endpoint has (`changed_at` is not one; IGDB answered 400 "Invalid Field" and no game got a publisher).

### Start animation

`features/startup/startup_splash.dart` (`StartupSplash`, wrapped around the router in `app.dart`) shows the start animation above the app when it starts: the Saturn of the brand mark (`SaturnSpinnerPainter`, the painter of `ShelfSpinner`) arrives over the sky with a glow, and the wordmark "Backlog Manager" appears letter by letter followed by one sweep of light, 3 s in all. It ends when the animation has run and the session check is over (`SessionLoading` holds it), then fades out over 0.5 s into the sign-in page or the shell; a click or a key press skips it (the key press is not consumed, no focus moves). It is shown once per start and not at all while the system asks for less motion, while "Animated Background" is off and in tests (`atmosphereMotion`).

### Profile picture

Settings > General > Account > "Profile Picture" (`features/settings/profile_picture_row.dart`): "Choose Picture" opens the system file dialog (`platform/image_file_picker.dart`), `squareAvatarPng` (`platform/avatar_image.dart`) crops the biggest centred square and scales it to 256 px as a PNG, and `UserApi.setAvatar` sends the bytes with `PUT /api/user/avatar`; "Remove" calls `DELETE /api/user/avatar`. The session user carries `id` and `avatarUpdatedAt` (the version); `UserAvatar` (`features/common/user_avatar.dart`) shows the picture in the sidebar, in the settings and for both members of a Shared Space (`SpaceMember.userId`, `avatarUpdatedAt`) and falls back to the initials while there is none, while it loads and when it cannot be read. The bytes are read once per version (`avatarBytesProvider`), so a new upload is read again and nothing else is.

### Update notification

`features/updates/` tells the user about a newer release and, where the install can replace itself, installs it in place (download, signature check, restart; the mechanism, the payload keys and the key handling are in [`APP_UPDATES.md`](APP_UPDATES.md)). `domain/app_update.dart` holds the pure part (`parseVersion`, `isNewerVersion` compare plain `X.Y.Z` numerically, `appReleaseFromJson` drops drafts, pre-releases, tags that are not a plain version and pages outside github.com); `data/release_source.dart` reads the newest release of the channel that has an `app-update.json`, else `releases/latest` of the repository (GitHub already leaves out drafts and pre-releases; 404 means no release), and the installed version from `package_info_plus`. The channel (`UpdateChannel`: Stable skips pre-releases, Preview takes them; a switch in the App Updates group, details in [`APP_UPDATES.md`](APP_UPDATES.md)) decides which releases of that list count.

- **On start:** `UpdateNotifier` (in `AppShell`) checks quietly in release builds only (`automaticUpdateCheckProvider`, so development and tests make no request); offline and rate-limit failures change nothing. A newer release shows the toast "Backlog Manager <version> is available" with "View release" once per session; the toast stays for a day unless another toast replaces it.
- **Settings > Updates (#430, a tab of its own between Backups and About):** "Check for updates" ("Checking..."), then "You are on the latest version.", "Version <x> is available." with the release notes and "View release", or "The update check failed. Try again later." The manual check reports failures.
- Releases published as pre-releases are offered on the **Preview** channel only; on **Stable**, the default since the cutover (#287), they are skipped.

### Duplicate games

The icon button next to "Sync IGDB" in the library toolbar opens "Duplicate games" (`features/duplicates/duplicates_sheet.dart`, logic in `domain/duplicates.dart`): every game that is in the personal backlog more than once, found on the client from the loaded entries. Entries are the same game when they share the title (case, outer and repeated spaces ignored, like the server's duplicate check) or the Steam App ID; entries linked by either end up in one group, so three entries chained by title and by app ID are one group. Renaming one of the entries in the inspector (for example a demo to "Name (Demo)") takes it out of a group that came from the same title. A group shows why it is one ("Same title", "Same Steam App ID", "Same title and Steam App ID"), its entries by age (the lowest ID, marked "(oldest)", is the one the others are compared with), and for every other entry what differs from the oldest as the usual minus/plus diff (genre, platform, status, owned, playtime, rating, note). "Delete" asks first, through the same confirmation as everywhere else, and the groups update as entries go.

### Performance

What costs hardware, the same on every platform (the Flutter code is shared; only the graphics backend differs):

- **Decorative motion** runs at about 30 frames per second, whatever the display does: the sky and the glow of a cover share `ThrottledClock` (`design/throttled_clock.dart`), the Freaky orbs skip every second frame of a 60 Hz display. The motion is slow, so this is not visible, and it halves the repaints of everything below them.
- **Blur** is the costliest part: the glass of the title bar, sidebar, inspector and status bar blurs a backdrop that changes with every tick of the moving sky. Settings → *Blur Effects* (device-local, on by default) turns it off and leaves the translucent tint; *Animated Background* and *Animated Glow* switch the motion off. For a slow graphics card, switch these three off first.
- Frames stop by themselves when the window is hidden or minimized (framework behaviour), lists and the cover grid are virtualized, covers decode at 420 px, and the cover image requests are deferred (`coverImageDelay`).
- Not measured here: frame times on real GPUs. The beta users compare with the switches and report in #286; to measure, run `task app:dev` in profile mode and turn on the performance overlay.

### Freaky orbs

`design/freaky_orbs.dart` (logic in `domain/orbs.dart`) paints the drifting orbs behind the whole window for the `freaky` theme, like `FreakyBackground.tsx` of the web client: 28 orbs of radius 40 to 160 with a random drift of at most 0.3 px per frame, wrapping at the edges, pulsing between 50 and 100 percent of their radius, alternately tinted with the glow and the accent colour at alpha 0.14 and added onto the atmosphere (`BlendMode.plus`). `AtmosphereBackground` shows them when the active theme id is `freaky` (not while colours are previewed in the theme creator, which uses another id) and the system does not ask for less motion; the layer takes no pointer input and is hidden from the semantics tree.

### Integration tests

`app/integration_test/main_flows_test.dart` runs the real app (real router, providers, generated client and screens) in a window against `integration_test/fake_backend.dart`, an `HttpClientAdapter` that answers the HTTP requests of the app from memory and keeps what the writes changed. The games databases (search, covers) are the same in-process double the widget tests use. Flows: sign in with a password and a two-factor code (and a wrong code), the library loads and groups by status, dropping a game on another group changes its status, editing a field in the inspector saves by itself, adding a game from the search through the creation tool, filtering and selecting.

Run them with `task app:test:integration` (a display is needed: on Linux a headless run is `Xvfb :99 -screen 0 1440x900x24 &` and `DISPLAY=:99 task app:test:integration`; the Linux build dependencies of the "Linux build" CI job apply, plus `libsecret-1-dev` and `xvfb`). The CI job "App Integration Tests" does this under `xvfb-run`. They use `flutter drive` rather than `flutter test integration_test`, which fails to build the app on a Linux runner. In a live window `tester.enterText` needs a `tester.pump()` before the app sees the text, and a tap on a tile below the window does not hit it, so the flows only use what is on screen.
